数据加密#

题目：某加密产品采用标准算法进行数据安全防护，某安全研究员通过逆向分析得到该产品的代码后发现，这段代码模拟了某商用密码库接口中可能存在的双重填充场景。请分析题目提供的代码文件，基于截获的密文及侧信道数据，恢复原始数据。 分析题目提供的task.py文件

代码做了双重填充，自定义padding(msg)，tmp = 16 - len(msg) % 16，返回bytes([tmp])*tmp + msg（前置填充）,再对上一步的结果做一次标准 PKCS#7 后置填充pad(message, 16, 'pkcs7')，用 AES-CBC 随机 IV 加密，但没有输出 IV。
可利用点为hint 泄漏 + 首块明文可预测，已知len(flag)=38，所以tmp = 16 - (38 mod 16) = 16 - 6 = 10，前置填充就是0x0a重复10字节，因而首块明文 P1 = 0x0a*10 + flag[:6]；又已知flag固定前缀 flag{，所以flag[:6] = b"flag{" + x，只有第6个字节x不确定（1 字节，256 种），而hint = key ⊕ P1(（按 16 字节整块异或）)，所以只要枚举x，就能恢复完整key。
P1 = Dec_k(C1) ⊕ IV，所以IV = Dec_k(C1) ⊕ P1，枚举出正确的key与P1后，就能算出IV，然后解密整个密文，再做PKCS#7 unpad，最后去掉前置的0x0a*10 得到原 flag。

数据审计#

题目1:#

证书合成。请根据题目提供的证书关键参数，合成私钥解密证书。请选手找到id为285的参数合成的证书（参考附件：params.csv）可以解密哪个流量包（参考附件：pcap.zip）。并将其流量包名称作为答案提交。若id为285的参数合成证书，可以解密“UT5NHVWo2Z.pacp”，则答案提交为UT5NHVWo2Z.pacp的32位小写MD5值如7cb41b100d1cfbcbdldeld795dac3fcb。

params.csv文件给了多行RSA私钥的关键参数（p、q、e），pcap.zip文件中有很多抓包，每个抓包里都有TLS 握手的服务器证书。某个抓包里的服务器证书公钥（n,e）与重建私钥对应的公钥一致，那这个私钥就能用于该抓包的TLS解密（证书/私钥匹配），所以不一定要把TLS流量解密出来,只要匹配证书公钥就能确定对应哪个流量包。

RSA 核心是一对密钥，公钥：(n, e)，私钥：(n, d) 以及一些加速参数，p和q是两个大质数，RSA 的模数n是n = p x q，RSA的安全性依赖于只有n很难分解出p,q。e是公钥指数,常见值是65537（十六进制0x10001），也可能是别的奇数。d是私钥指数，d ≡ e⁻¹ (mod φ(n))，欧拉函数φ(n) = (p-1)(q-1)，所以只要知道 p,q,e，就可以计算出n和d，从而完整重建私钥。

  • 计算模数：n = p*q
  • 计算欧拉函数：φ = (p-1)*(q-1)
  • 计算模逆得到私钥指数：d = e^{-1} mod φ，python中是d = pow(e, -1, φ)
  • CRT 参数（非必要）：dp = d mod (p-1)，dq = d mod (q-1)，iqmp = q^{-1} mod p（qInv）

题目2:#

证书解密。请根据上面的题目对每个流量包进行解密，并得到明文。请选手找到“王梅”的手机号，并进行答案提交。若找到“王梅”的手机号为15306364252,则提交答案为15306364252的32位小写MD5值如8ce2927e85dde243ec8ed0754fd7781f。

每个 pcap 中都有 TLS 握手报文，包含 Certificate。证书里包含 RSA 公钥 modulus：n = p*q，题目给的params.csv每行提供一组 (id, p, q, e)，所以流程是：从 pcap 中提取证书 DER，解析 X509 证书，取 RSA 公钥 modulusn，在params.csv中找到n相同的那一行，即该 pcap 对应的 RSA 参数；由 (p,q,e) 反推私钥并导出 PEM，phi = (p-1)(q-1)，d = e^{-1} mod phi，计算 CRT 参数 dp,dq,qi，导出 PEM 私钥文件idXXX.pem；在 Kali 上使用 tshark 解密 TLS，输出 follow stream 的明文；解密得到的明文可能出现多种编码形式：接出现：王梅，Unicode 转义：\\u738b\\u6885，URL 编码：%5Cu738b%5Cu6885。

tshark 4.6.0 中旧的 tls.keys_list 已被标记为 obsolete，采用新的 RSA Keys UAT 配置方式 -o uat:rsa_keys:“/abs/path/key.pem”,"" -z follow,tls,utf-8,<tcp.stream> 使用 -2（two-pass）提高 TCP 重组与解密稳定性

  • 对每个流执行：tshark -2 -o uat:rsa_keys:"key.pem","" -z follow,tls,utf-8,<stream>，保存明文到out_task2/decrypted/*.txt

题目3:#

数据核验。为了安全可靠，该系统在请求包设置了Authorization头部字段。该字段是使用JWT进行加密的，每个人的密钥为了安全考虑设置成自己姓名的拼音。请选手解密JWT身份认证核对信息是否与请求体中的内容是否一致。若非一致，该用户可能在进行越权访问。请选手统计出有多少个账号进行越权。若有101个账号进行越权，则答案提交为101的32位小写MD5值如38b3eff8baf56627478ec76a704e9b52。

基于解密后的HTTP明文继续处理，HTTP Header：Authorization: Bearer <JWT>，HTTP Body：JSON 请求体（包含 username/phone 等字段），JWT 的格式固定为：header.payload.signature，其中header与payload均为base64url编码的JSON，提取Authorization中的JWT，对JWT的第二段payload做base64url解码，json.loads()得到payload字典，若payload["username"] != body["username"]或payload["phone"] != body["phone"]认为该账号存在越权行为，根据题目，对越权账号去重。

  • 遍历 500 个pcap，逐个得到HTTP明文
  • 用正则从headers提取JWT：Authorization: Bearer <token>
  • 从明文body解析JSON
  • JWT payload 解析：payload = json.loads(base64url_decode(jwt.split('.')[1]))
  • 比对字段username/phone：不一致则将payload["username"]记录到over_users集合
  • 最终输出：越权账号去重数量len(over_users),该数量的 MD5（32位小写）,越权账号名单。
